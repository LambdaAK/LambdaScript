\begin{abstract}
We present LambdaScript, a statically-typed functional programming language inspired by Haskell and OCaml. LambdaScript features Hindley-Milner type inference, polymorphic algebraic data types, comprehensive pattern matching, and first-class functions with closures. The language supports advanced features including mutually recursive type definitions, list comprehensions, and operators as first-class values. This paper describes both the formal semantics and the complete implementation of LambdaScript, including the design of the type system, operational semantics, and the architecture of a full interpreter pipeline consisting of lexical analysis, parser combinators, constraint-based type inference, and environment-based evaluation. The implementation is validated through 1200 unit tests covering complex real-world algorithms including red-black trees, interpreters, and graph traversal.
\end{abstract}

\section{Introduction}

Statically-typed functional programming languages such as Haskell, OCaml, and Standard ML provide powerful abstractions for writing correct programs through algebraic data types, pattern matching, and polymorphic type inference. The Hindley-Milner type system enables programmers to write code without explicit type annotations while maintaining complete type safety through automatic type inference. However, understanding how these features interact---both formally through typing rules and operationally through implementation---requires navigating complex, mature language ecosystems with decades of accumulated features and optimizations.

This paper presents \textbf{LambdaScript}, a functional programming language designed to demonstrate that rigorous formal semantics and practical implementation can coexist harmoniously. LambdaScript features a complete Hindley-Milner type inference system, polymorphic algebraic data types, comprehensive pattern matching, and advanced features including mutually recursive type definitions. Rather than merely describing theoretical properties, we provide both a complete formal semantics and a fully implemented interpreter validated through extensive testing.

A key contribution of LambdaScript is its treatment of \textbf{mutually recursive algebraic data types}, which enable natural representation of complex data structures such as trees with forests, abstract syntax trees with multiple node types, and graph-based structures. While languages like OCaml and Haskell support such types, their formal semantics and implementation present subtle challenges in constraint generation, type environment management, and ensuring that recursive references are properly resolved during type checking. LambdaScript addresses these challenges with a clean syntax using the \texttt{and} keyword and a carefully designed type checking algorithm that extends the standard Hindley-Milner approach.

The implementation consists of a complete interpreter pipeline: a lexer that tokenizes source code, a parser built using parser combinators for compositional grammar definitions, a constraint-based type checker implementing Hindley-Milner inference with extensions for recursive types, and an environment-based evaluator that handles closures, recursion, and pattern matching. The entire system is written in OCaml and validated through 1200 unit tests covering type inference edge cases, evaluation correctness, and real-world algorithms including red-black tree operations.

The main contributions of this paper are:
\begin{itemize}
\item A formal semantics for a functional language with mutually recursive algebraic data types, including complete typing rules and operational semantics
\item A complete implementation architecture demonstrating how theory translates to practice, including lexer, parser combinators, constraint-based type inference, and environment-based evaluation
\item Extensions to the standard Hindley-Milner algorithm to support mutually recursive types and proper handling of fixed-point types
\item Validation through 1200 unit tests demonstrating correctness on complex algorithms including red-black trees, showcasing the language's expressiveness
\end{itemize}

The remainder of this paper is organized as follows. Section~II presents examples demonstrating LambdaScript's features, building intuition before formal treatment. Section~III describes the type system design, including polymorphism, algebraic data types, and type inference. Section~IV provides detailed formal semantics with typing rules and operational semantics. Section~V details the implementation architecture of each pipeline component. Section~VI presents testing methodology and evaluation results. Section~VII concludes with reflections and future directions.

\section{Examples}

This section presents examples that demonstrate LambdaScript's core features, building intuition for the formal treatment in subsequent sections. We showcase algebraic data types, pattern matching, polymorphism, and higher-order functions through practical examples.

\subsection{Polymorphic List Data Type}

We begin by defining a polymorphic list type using recursive algebraic data types. LambdaScript uses the \texttt{type rec} keyword for recursive type definitions and the \texttt{'a} syntax for type variables, following OCaml conventions.

\begin{quote}
\small
\begin{verbatim}
type rec List<'a> = 
  | Nil 
  | Cons of ('a, List<'a>)
\end{verbatim}
\end{quote}

This definition introduces two constructors: \texttt{Nil} represents the empty list, and \texttt{Cons} takes a tuple containing an element of type \texttt{'a} and the rest of the list. The type parameter \texttt{'a} makes this list polymorphic, allowing lists of any type.

With the list type defined, we can implement fundamental higher-order functions that operate over lists.

\subsubsection{Map Function}

The \texttt{map} function applies a function to each element of a list:

\begin{quote}
\small
\begin{verbatim}
let rec map f lst =
  case lst do
  | Nil -> Nil
  | Cons (h, t) -> Cons (f h, map f t)
\end{verbatim}
\end{quote}

The type system infers the polymorphic type:
\begin{center}
\texttt{map : ('a -> 'b) -> List<'a> -> List<'b>}
\end{center}

This demonstrates parametric polymorphism: \texttt{map} works for any input type \texttt{'a} and output type \texttt{'b}, as long as the function \texttt{f} has type \texttt{'a -> 'b}.

Example usage:
\begin{quote}
\small
\begin{verbatim}
let double = fn x -> x * 2 in
let numbers = Cons (1, Cons (2, Nil)) in
map double numbers
(* Result: Cons (2, Cons (4, Nil)) *)
\end{verbatim}
\end{quote}

\subsubsection{Reduce Function}

The \texttt{reduce} function (also known as fold) combines list elements using a binary operator:

\begin{quote}
\small
\begin{verbatim}
let rec reduce op acc lst =
  case lst do
  | Nil -> acc
  | Cons (h, t) -> reduce op (op acc h) t
\end{verbatim}
\end{quote}

Inferred type: \texttt{reduce : ('b -> 'a -> 'b) -> 'b -> List<'a> -> 'b}

The type signature shows that \texttt{reduce} can produce a result of a different type (\texttt{'b}) than the list elements (\texttt{'a}), demonstrating the power of polymorphic type inference.

Example summing a list:
\begin{quote}
\small
\begin{verbatim}
let add = fn x -> fn y -> x + y in
let numbers = Cons (1, Cons (2, Nil)) in
reduce add 0 numbers
(* Result: 3 *)
\end{verbatim}
\end{quote}

\subsection{Option Monad}

The Option type represents computations that may fail, providing a type-safe alternative to null values. We define it as a sum type with two constructors:

\begin{quote}
\small
\begin{verbatim}
type Option<'a> = 
  | None 
  | Some of 'a
\end{verbatim}
\end{quote}

\texttt{None} represents absence of a value, while \texttt{Some} wraps a present value of type \texttt{'a}.

\subsubsection{Monadic Bind Operation}

The bind operation chains optional computations. In LambdaScript, we can define it as an operator:

\begin{quote}
\small
\begin{verbatim}
let (>>=) opt f =
  case opt do
  | None -> None
  | Some x -> f x
\end{verbatim}
\end{quote}

Inferred type: \texttt{(>>=) : Option<'a> -> ('a -> Option<'b>) -> Option<'b>}

This type signature is the hallmark of monadic bind: it takes an \texttt{Option<'a>}, a function from \texttt{'a} to \texttt{Option<'b>}, and produces \texttt{Option<'b>}. If the input is \texttt{None}, the computation short-circuits; otherwise, the function is applied to the unwrapped value.

\subsubsection{Return Operation}

The \texttt{return} operation (called \texttt{pure} in some languages) lifts a value into the Option context:

\begin{quote}
\small
\begin{verbatim}
let return x = Some x
\end{verbatim}
\end{quote}

Inferred type: \texttt{return : 'a -> Option<'a>}

\subsubsection{Map for Option}

Mapping a function over an optional value:

\begin{quote}
\small
\begin{verbatim}
let map_opt f opt =
  case opt do
  | None -> None
  | Some x -> Some (f x)
\end{verbatim}
\end{quote}

Inferred type: \texttt{map\_opt : ('a -> 'b) -> Option<'a> -> Option<'b>}

\subsubsection{Example: Safe Division}

These operations enable safe computation chains. Consider safe division:

\begin{quote}
\small
\begin{verbatim}
let safe_div x y =
  if y == 0 then None
  else Some (x / y)
in

let compute x y z =
  (safe_div x y) >>= (fn result1 ->
    (safe_div result1 z) >>= (fn result2 ->
      return result2))
in

compute 100 10 2
(* Result: Some 5 *)

compute 100 0 2
(* Result: None *)
\end{verbatim}
\end{quote}

The first computation succeeds: $100 / 10 / 2 = 5$. The second short-circuits at division by zero, returning \texttt{None} without attempting the second division. This demonstrates how the Option monad handles errors compositionally through pattern matching and type safety, without exceptions or null pointer errors.

These examples illustrate several key features of LambdaScript: algebraic data types enable clean data modeling, pattern matching provides exhaustive case analysis, parametric polymorphism allows generic code, and the type system infers complex types including higher-rank polymorphism in monadic operations.

\section{Type System}

LambdaScript features a Hindley-Milner type system with support for parametric polymorphism, algebraic data types, and mutually recursive type definitions. The type system is both sound and complete: every well-typed program has a principal type, and type inference always succeeds when a valid typing exists.

\subsection{Basic Types and Type Inference}

LambdaScript includes primitive types (\texttt{int}, \texttt{float}, \texttt{bool}, \texttt{string}, \texttt{char}, \texttt{unit}), composite types (functions, lists, tuples), and user-defined algebraic data types. The type checker automatically infers types without requiring explicit annotations:

\begin{quote}
\small
\begin{verbatim}
let x = 42
(* Inferred: x : int *)

let add x y = x + y
(* Inferred: add : int -> int -> int *)

let id x = x
(* Inferred: id : 'a -> 'a *)
\end{verbatim}
\end{quote}

The identity function \texttt{id} receives the polymorphic type \texttt{'a -> 'a}, where \texttt{'a} is a type variable that can be instantiated to any type. This demonstrates \textbf{let-polymorphism}: functions bound with \texttt{let} can be used at multiple types in different contexts.

\subsection{Type Variables and Generalization}

Type variables represent unknown types during inference. When a function is defined with \texttt{let}, the type checker \textbf{generalizes} over all unconstrained type variables, introducing universal quantifiers. Consider:

\begin{quote}
\small
\begin{verbatim}
let compose f g x = f (g x)
(* Type: ('b -> 'c) -> ('a -> 'b) -> 'a -> 'c *)
\end{verbatim}
\end{quote}

The type checker generates fresh type variables for \texttt{f}, \texttt{g}, and \texttt{x}, then analyzes the function application \texttt{f (g x)}:
\begin{itemize}
\item \texttt{g x} requires \texttt{g : 'a -> 'b} for some \texttt{'b}
\item \texttt{f (g x)} requires \texttt{f : 'b -> 'c} for some \texttt{'c}
\item The result has type \texttt{'c}
\end{itemize}

After constraint solving, the system generalizes to produce the most general type with three independent type variables.

\subsection{Algebraic Data Types}

Algebraic data types define new types using constructors. Each constructor may carry a payload:

\begin{quote}
\small
\begin{verbatim}
type Result<'a, 'b> = 
  | Ok of 'a
  | Error of 'b
\end{verbatim}
\end{quote}

When this definition is processed, the type checker:
\begin{enumerate}
\item Introduces \texttt{Result} as a new type constructor taking two type parameters
\item Creates constructor types: \texttt{Ok : 'a -> Result<'a, 'b>} and \texttt{Error : 'b -> Result<'a, 'b>}
\item Adds these constructors to the typing environment
\end{enumerate}

Users can then construct and match on values:

\begin{quote}
\small
\begin{verbatim}
let safe_sqrt x =
  if x < 0 then Error "negative"
  else Ok (sqrt x)
(* Type: int -> Result<float, string> *)

let handle result =
  case result do
  | Ok v -> v
  | Error msg -> 0.0
(* Type: Result<float, 'a> -> float *)
\end{verbatim}
\end{quote}

\subsection{Recursive Types}

Recursive types reference themselves in their definition. LambdaScript uses \textbf{isorecursive} semantics with explicit \texttt{type rec} declarations:

\begin{quote}
\small
\begin{verbatim}
type rec Tree<'a> = 
  | Leaf of 'a
  | Node of ('a, Tree<'a>, Tree<'a>)
\end{verbatim}
\end{quote}

Internally, this is represented as a fixed-point type $\mu$\texttt{Tree}. The type checker ensures that:
\begin{itemize}
\item Each recursive occurrence is properly parameterized
\item Constructor payloads are type-checked in an environment containing the recursive type
\item Pattern matching correctly unfolds the recursive type
\end{itemize}

Example usage demonstrates automatic type inference through recursive structures:

\begin{quote}
\small
\begin{verbatim}
let rec height tree =
  case tree do
  | Leaf _ -> 1
  | Node (_, l, r) -> 
      1 + (if height l > height r 
           then height l else height r)
(* Type: Tree<'a> -> int *)
\end{verbatim}
\end{quote}

\subsection{Mutually Recursive Types}

A key contribution of LambdaScript is clean support for mutually recursive type definitions using the \texttt{and} keyword. Multiple types can reference each other:

\begin{quote}
\small
\begin{verbatim}
type rec Tree<'a> = 
  | Leaf of 'a 
  | Node of ('a, Forest<'a>)
and Forest<'a> = 
  | Empty 
  | Trees of (Tree<'a>, Forest<'a>)
\end{verbatim}
\end{quote}

The type checker processes mutually recursive types by:
\begin{enumerate}
\item Adding all type names to the environment simultaneously before processing any constructors
\item Type-checking each constructor's payload in the extended environment
\item Ensuring all type parameters are consistently applied across mutual references
\item Verifying that cycles are properly guarded by constructors (no infinite types)
\end{enumerate}

This enables natural expression of complex data structures:

\begin{quote}
\small
\begin{verbatim}
let rec tree_size t =
  case t do
  | Leaf _ -> 1
  | Node (_, forest) -> 1 + forest_size forest
and forest_size f =
  case f do
  | Empty -> 0
  | Trees (t, rest) -> 
      tree_size t + forest_size rest
(* tree_size : Tree<'a> -> int
   forest_size : Forest<'a> -> int *)
\end{verbatim}
\end{quote}

The implementation extends the standard Hindley-Milner unification algorithm to handle fixed-point types and ensures that type variable substitutions propagate correctly across the mutual recursion group.

\subsection{Type Annotations}

While type inference eliminates most annotations, LambdaScript allows optional type annotations for documentation and disambiguation:

\begin{quote}
\small
\begin{verbatim}
let f (x: int) : int = x + 1

let g (x: int) : int = x * 2
\end{verbatim}
\end{quote}

Type annotations are checked for consistency with inferred types. If an annotation conflicts with the inferred type, the type checker reports an error.

\section{Syntax}

We present the complete syntax of LambdaScript in Extended Backus-Naur Form (EBNF). Non-terminals are written in italics, terminals in \texttt{typewriter font}, and metavariables are defined below.

\textbf{Expressions:}
\begin{align*}
e ::= &\; n \mid b \mid s \mid c \mid () \mid x \\
    | &\; e_1 \; \texttt{op} \; e_2 \\
    | &\; \texttt{fn} \; p \; \texttt{->} \; e \\
    | &\; e_1 \; e_2 \\
    | &\; \texttt{let} \; p \; \texttt{=} \; e_1 \; \texttt{in} \; e_2 \\
    | &\; \texttt{let} \; \texttt{rec} \; x \; p^* \; \texttt{=} \; e_1 \; \texttt{in} \; e_2 \\
    | &\; \texttt{if} \; e_1 \; \texttt{then} \; e_2 \; \texttt{else} \; e_3 \\
    | &\; \texttt{case} \; e \; \texttt{do} \; (\texttt{|} \; p \; \texttt{->} \; e)^+ \\
    | &\; [ \; ] \mid e_1 \; \texttt{::} \; e_2 \mid [ \; e_1, \ldots, e_n \; ] \\
    | &\; ( e_1, \ldots, e_n ) \\
    | &\; C \mid C \; e
\end{align*}

\textbf{Patterns:}
\begin{align*}
p ::= &\; \_ \mid x \mid n \mid b \mid s \mid c \mid () \\
    | &\; [ \; ] \mid p_1 \; \texttt{::} \; p_2 \\
    | &\; ( p_1, \ldots, p_n ) \\
    | &\; C \mid C \; p
\end{align*}

\textbf{Types:}
\begin{align*}
\tau ::= &\; \texttt{int} \mid \texttt{float} \mid \texttt{bool} \mid \texttt{string} \mid \texttt{char} \mid \texttt{unit} \\
       | &\; \alpha \mid \tau_1 \; \texttt{->} \; \tau_2 \mid [ \; \tau \; ] \\
       | &\; ( \tau_1, \ldots, \tau_n ) \\
       | &\; T \mid T \; \texttt{<} \tau_1, \ldots, \tau_n \texttt{>}
\end{align*}

\textbf{Type Definitions:}
\begin{align*}
\textit{typedef} ::= &\; \texttt{type} \; T \; \texttt{<} \alpha_1, \ldots, \alpha_n \texttt{>} \; \texttt{=} \; \tau \\
                   | &\; \texttt{type} \; T \; \texttt{<} \alpha_1, \ldots, \alpha_n \texttt{>} \; \texttt{=} \; (\texttt{|} \; C \; [\texttt{of} \; \tau])^+ \\
                   | &\; \texttt{type} \; \texttt{rec} \; T \; \texttt{<} \alpha_1, \ldots, \alpha_n \texttt{>} \; \texttt{=} \; (\texttt{|} \; C \; [\texttt{of} \; \tau])^+ \\
                   | &\; \texttt{type} \; \texttt{rec} \; T_1 \; \texttt{<} \alpha^* \texttt{>} \; \texttt{=} \; (\texttt{|} \; C \; [\texttt{of} \; \tau])^+ \\
                   & \; (\texttt{and} \; T_i \; \texttt{<} \alpha^* \texttt{>} \; \texttt{=} \; (\texttt{|} \; C \; [\texttt{of} \; \tau])^+)^+
\end{align*}

\textbf{Programs:}
\begin{align*}
\textit{program} ::= &\; (\textit{typedef} \mid \texttt{let} \; p \; \texttt{=} \; e \mid \texttt{let} \; \texttt{rec} \; x \; p^* \; \texttt{=} \; e)^*
\end{align*}

\textbf{Metavariables:}
\begin{itemize}
\item $x$ ranges over variables (identifiers beginning with lowercase letters)
\item $n$ ranges over integer literals
\item $b$ ranges over boolean literals (\texttt{true}, \texttt{false})
\item $s$ ranges over string literals
\item $c$ ranges over character literals
\item $C$ ranges over constructors (identifiers beginning with uppercase letters)
\item $T$ ranges over type constructors
\item $\alpha$ ranges over type variables (identifiers beginning with \texttt{'})
\item $\texttt{op}$ ranges over binary operators: \texttt{+}, \texttt{-}, \texttt{*}, \texttt{/}, \texttt{\%}, \texttt{==}, \texttt{!=}, \texttt{<}, \texttt{>}, \texttt{<=}, \texttt{>=}, \texttt{\&\&}, \texttt{||}
\end{itemize}

\textbf{Notation:}
\begin{itemize}
\item $e^*$ denotes zero or more occurrences of $e$
\item $e^+$ denotes one or more occurrences of $e$
\item $[e]$ denotes an optional occurrence of $e$
\item $(e_1 \mid e_2)$ denotes a choice between $e_1$ and $e_2$
\end{itemize}

\section{Formal Semantics}

\subsection{Overview}

We now present the formal semantics of LambdaScript, providing a rigorous mathematical foundation for both the type system and runtime behavior. Formal semantics serve multiple purposes: they enable precise reasoning about program behavior, provide unambiguous specifications for implementers, and allow formal verification of type soundness and other properties.

Our semantic framework consists of two complementary components:

\textbf{Static Semantics} defines the type system through typing judgments of the form $\Gamma \vdash e : \tau$, read as ``under type environment $\Gamma$, expression $e$ has type $\tau$.'' The static semantics specify when programs are well-typed and determine the principal types of expressions through constraint-based type inference. We formalize the Hindley-Milner algorithm, including constraint generation, unification, and generalization. Special attention is given to the treatment of algebraic data types and mutually recursive type definitions, which require careful handling of type environments and fixed-point types.

\textbf{Dynamic Semantics} defines program evaluation through operational semantics. We use large-step (natural) operational semantics with evaluation judgments of the form $\langle e, \rho \rangle \Downarrow v$, indicating that expression $e$ in environment $\rho$ evaluates to value $v$. Large-step semantics directly relate expressions to their final values, making the evaluation rules more intuitive and closely aligned with the implementation. The dynamic semantics specify how values are computed, how functions are applied, how pattern matching proceeds, and how recursion is handled through environment-based closure semantics.

The static and dynamic semantics are designed to satisfy \textbf{type soundness}: well-typed programs do not get stuck during evaluation. This is formalized through the type preservation theorem: if $\Gamma \vdash e : \tau$ and $\langle e, \rho \rangle \Downarrow v$, then $v$ has type $\tau$. While we do not provide complete proofs here, the semantics are structured to facilitate such proofs.

We adopt standard mathematical notation: $\Gamma$ denotes type environments mapping variables to types, $\rho$ denotes value environments mapping variables to values, and $\tau$ ranges over types. Substitutions are written $[\tau'/\alpha]\tau$ for replacing type variable $\alpha$ with type $\tau'$ in type $\tau$. Function types are written $\tau_1 \rightarrow \tau_2$, list types as $[\tau]$, and tuple types as $(\tau_1, \tau_2, \ldots, \tau_n)$.

\subsection{Static Semantics}

The static semantics of LambdaScript defines a type system based on the Hindley-Milner approach with extensions for algebraic data types and mutually recursive type definitions. We present typing rules, constraint generation, unification, and generalization.

\subsubsection{Notation and Definitions}

\textbf{Types and Type Schemes:}

Types $\tau$ are classified as:
\begin{itemize}
\item Primitive types: \texttt{int}, \texttt{bool}, \texttt{string}, \texttt{char}, \texttt{unit}
\item Type variables: $\alpha, \beta, \gamma, \ldots$
\item Function types: $\tau_1 \to \tau_2$
\item List types: $[\tau]$
\item Tuple types: $(\tau_1, \ldots, \tau_n)$
\item Algebraic data types: $T\langle\tau_1, \ldots, \tau_n\rangle$
\item Recursive types: $\mu T.\tau$
\end{itemize}

Type schemes $\sigma$ extend types with universal quantification:
$$\sigma ::= \tau \mid \forall \alpha.\sigma$$

\textbf{Type Environments:}

A type environment $\Gamma$ is a finite map from variables to type schemes, written $\{x_1 : \sigma_1, \ldots, x_n : \sigma_n\}$. We write:
\begin{itemize}
\item $\Gamma(x)$ for environment lookup
\item $\Gamma, x : \sigma$ for environment extension
\item $\emptyset$ for the empty environment
\item $FV(\Gamma)$ for the set of free type variables in $\Gamma$
\item $FV(\tau)$ for the set of free type variables in $\tau$
\end{itemize}

\textbf{Substitutions:}

A type substitution $S$ is a finite map from type variables to types, written $[\tau_1/\alpha_1, \ldots, \tau_n/\alpha_n]$. We write:
\begin{itemize}
\item $S(\tau)$ for applying substitution $S$ to type $\tau$
\item $S(\Gamma)$ for applying substitution to all types in $\Gamma$
\item $S_2 \circ S_1$ for composition: $(S_2 \circ S_1)(\tau) = S_2(S_1(\tau))$
\item $\texttt{id}$ for the identity substitution
\end{itemize}

\textbf{Typing Judgment:}

The primary judgment form is:
$$\Gamma \vdash e : \tau$$
read as ``under type environment $\Gamma$, expression $e$ has type $\tau$.''

\textbf{Generalization and Instantiation:}

Generalization introduces universal quantifiers:
$$\text{gen}(\Gamma, \tau) = \forall \{\alpha_1, \ldots, \alpha_n\}.\tau$$
where $\{\alpha_1, \ldots, \alpha_n\} = FV(\tau) \setminus FV(\Gamma)$.

Instantiation removes universal quantifiers by substituting fresh type variables:
$$\text{inst}(\forall \alpha.\sigma) = \sigma[\beta/\alpha]$$
where $\beta$ is fresh. For non-quantified types: $\text{inst}(\tau) = \tau$.

\subsubsection{Typing Rules}

We present the typing rules for all LambdaScript expressions.

\textbf{Literals:}

$$\frac{}{\Gamma \vdash n : \texttt{int}}
\quad
\frac{}{\Gamma \vdash b : \texttt{bool}}
\quad
\frac{}{\Gamma \vdash s : \texttt{string}}
\quad
\frac{}{\Gamma \vdash c : \texttt{char}}
\quad
\frac{}{\Gamma \vdash () : \texttt{unit}}$$

\textbf{Variables:}

$$\frac{x : \sigma \in \Gamma \quad \tau = \text{inst}(\sigma)}{\Gamma \vdash x : \tau}$$

Variables are looked up in the environment and their type schemes are instantiated with fresh type variables.

\textbf{Functions:}

$$\frac{\Gamma, x : \tau_1 \vdash e : \tau_2}{\Gamma \vdash \texttt{fn} \; x \; \texttt{->} \; e : \tau_1 \to \tau_2}$$

For pattern-based functions:
$$\frac{p : \tau_1 \leadsto \Gamma' \quad \Gamma, \Gamma' \vdash e : \tau_2}{\Gamma \vdash \texttt{fn} \; p \; \texttt{->} \; e : \tau_1 \to \tau_2}$$

where $p : \tau \leadsto \Gamma'$ means pattern $p$ matches values of type $\tau$ and produces bindings $\Gamma'$.

\textbf{Application:}

$$\frac{\Gamma \vdash e_1 : \tau_1 \to \tau_2 \quad \Gamma \vdash e_2 : \tau_1}{\Gamma \vdash e_1 \; e_2 : \tau_2}$$

\textbf{Let Binding (Polymorphic):}

$$\frac{\Gamma \vdash e_1 : \tau_1 \quad \Gamma, x : \text{gen}(\Gamma, \tau_1) \vdash e_2 : \tau_2}{\Gamma \vdash \texttt{let} \; x = e_1 \; \texttt{in} \; e_2 : \tau_2}$$

Let-bound variables are generalized, allowing polymorphic usage in $e_2$.

\textbf{Recursive Let Binding:}

$$\frac{\Gamma, f : \tau_1 \to \tau_2 \vdash \texttt{fn} \; x \; \texttt{->} \; e_1 : \tau_1 \to \tau_2 \quad \Gamma, f : \forall \{\alpha\}.(\tau_1 \to \tau_2) \vdash e_2 : \tau}{\Gamma \vdash \texttt{let rec} \; f \; x = e_1 \; \texttt{in} \; e_2 : \tau}$$

The recursive function $f$ is available in its own body with a monomorphic type, then generalized for use in $e_2$.

\textbf{Conditional:}

$$\frac{\Gamma \vdash e_1 : \texttt{bool} \quad \Gamma \vdash e_2 : \tau \quad \Gamma \vdash e_3 : \tau}{\Gamma \vdash \texttt{if} \; e_1 \; \texttt{then} \; e_2 \; \texttt{else} \; e_3 : \tau}$$

Both branches must have the same type.

\textbf{Pattern Matching:}

$$\frac{\Gamma \vdash e : \tau \quad \forall i.\; p_i : \tau \leadsto \Gamma_i \quad \Gamma, \Gamma_i \vdash e_i : \tau'}{\Gamma \vdash \texttt{case} \; e \; \texttt{do} \; \{p_i \to e_i\}^n_{i=1} : \tau'}$$

All patterns must match the scrutinee type, and all branches must have the same result type.

\textbf{Lists:}

$$\frac{}{\Gamma \vdash [] : [\alpha]}
\quad
\frac{\Gamma \vdash e_1 : \tau \quad \Gamma \vdash e_2 : [\tau]}{\Gamma \vdash e_1 :: e_2 : [\tau]}$$

Empty lists are polymorphic; cons requires consistent element types.

\textbf{Tuples:}

$$\frac{\Gamma \vdash e_1 : \tau_1 \quad \cdots \quad \Gamma \vdash e_n : \tau_n}{\Gamma \vdash (e_1, \ldots, e_n) : (\tau_1, \ldots, \tau_n)}$$

\textbf{Constructors:}

For a constructor $C : \tau \to T\langle\alpha_1, \ldots, \alpha_n\rangle$ in the environment:

$$\frac{}{\Gamma \vdash C : \tau[\tau_1/\alpha_1, \ldots, \tau_n/\alpha_n] \to T\langle\tau_1, \ldots, \tau_n\rangle}$$

$$\frac{\Gamma \vdash e : \tau}{\Gamma \vdash C \; e : T\langle\ldots\rangle}$$

Constructors are instantiated with fresh type variables when used.

\textbf{Binary Operators:}

$$\frac{\Gamma \vdash e_1 : \texttt{int} \quad \Gamma \vdash e_2 : \texttt{int}}{\Gamma \vdash e_1 \; \texttt{+} \; e_2 : \texttt{int}}$$

Similar rules apply for other arithmetic operators (\texttt{-}, \texttt{*}, \texttt{/}, \texttt{\%}).

$$\frac{\Gamma \vdash e_1 : \tau \quad \Gamma \vdash e_2 : \tau}{\Gamma \vdash e_1 \; \texttt{==} \; e_2 : \texttt{bool}}$$

Comparison operators require both operands to have the same type.

$$\frac{\Gamma \vdash e_1 : \texttt{bool} \quad \Gamma \vdash e_2 : \texttt{bool}}{\Gamma \vdash e_1 \; \texttt{\&\&} \; e_2 : \texttt{bool}}$$

Logical operators require boolean operands.

\subsubsection{Pattern Typing}

Pattern typing judgments have the form $p : \tau \leadsto \Gamma$, indicating that pattern $p$ matches values of type $\tau$ and produces bindings $\Gamma$.

\textbf{Variable Pattern:}
$$x : \tau \leadsto \{x : \tau\}$$

\textbf{Wildcard Pattern:}
$$\_ : \tau \leadsto \emptyset$$

\textbf{Literal Patterns:}
$$n : \texttt{int} \leadsto \emptyset
\quad
b : \texttt{bool} \leadsto \emptyset
\quad
() : \texttt{unit} \leadsto \emptyset$$

\textbf{List Patterns:}
$$[] : [\alpha] \leadsto \emptyset$$

$$\frac{p_1 : \tau \leadsto \Gamma_1 \quad p_2 : [\tau] \leadsto \Gamma_2}{p_1 :: p_2 : [\tau] \leadsto \Gamma_1 \cup \Gamma_2}$$

\textbf{Tuple Patterns:}
$$\frac{p_1 : \tau_1 \leadsto \Gamma_1 \quad \cdots \quad p_n : \tau_n \leadsto \Gamma_n}{(p_1, \ldots, p_n) : (\tau_1, \ldots, \tau_n) \leadsto \Gamma_1 \cup \cdots \cup \Gamma_n}$$

\textbf{Constructor Patterns:}
$$C : T\langle\tau_1, \ldots, \tau_n\rangle \leadsto \emptyset$$

$$\frac{p : \tau \leadsto \Gamma}{C \; p : T\langle\ldots\rangle \leadsto \Gamma}$$

where $C$ has type $\tau \to T\langle\ldots\rangle$.

\subsubsection{Constraint-Based Type Inference}

LambdaScript implements type inference using constraint generation and unification, following Algorithm W.

\textbf{Constraint Generation:}

The function $\mathcal{C}(\Gamma, e)$ generates a pair $(\tau, C)$ where $\tau$ is the inferred type (possibly containing fresh type variables) and $C$ is a set of type equality constraints.

\textit{Examples:}

\begin{align*}
\mathcal{C}(\Gamma, n) &= (\texttt{int}, \emptyset) \\
\mathcal{C}(\Gamma, x) &= (\text{inst}(\Gamma(x)), \emptyset) \\
\mathcal{C}(\Gamma, e_1 \; e_2) &= (\beta, C_1 \cup C_2 \cup \{(\tau_1, \tau_2 \to \beta)\})
\end{align*}

where $(\tau_1, C_1) = \mathcal{C}(\Gamma, e_1)$, $(\tau_2, C_2) = \mathcal{C}(\Gamma, e_2)$, and $\beta$ is fresh.

\begin{align*}
\mathcal{C}(\Gamma, \texttt{fn} \; x \; \texttt{->} \; e) &= (\alpha \to \tau, C)
\end{align*}

where $\alpha$ is fresh, $(\tau, C) = \mathcal{C}(\Gamma \cup \{x : \alpha\}, e)$.

\begin{align*}
\mathcal{C}(\Gamma, \texttt{if} \; e_1 \; \texttt{then} \; e_2 \; \texttt{else} \; e_3) &= (\tau_2, C_1 \cup C_2 \cup C_3 \cup \{(\tau_1, \texttt{bool}), (\tau_2, \tau_3)\})
\end{align*}

where $(\tau_i, C_i) = \mathcal{C}(\Gamma, e_i)$.

\textbf{Unification:}

The unification algorithm $\mathcal{U}(C)$ takes a set of constraints and computes a most general unifier (MGU), a substitution $S$ satisfying all constraints.

\textit{Unification rules:}

\begin{align*}
\mathcal{U}(\emptyset) &= \texttt{id} \\
\mathcal{U}(\{(\tau, \tau)\} \cup C) &= \mathcal{U}(C) \\
\mathcal{U}(\{(\alpha, \tau)\} \cup C) &= [\tau/\alpha] \circ \mathcal{U}([\tau/\alpha]C) \quad \text{if } \alpha \notin FV(\tau) \\
\mathcal{U}(\{(\tau, \alpha)\} \cup C) &= [\tau/\alpha] \circ \mathcal{U}([\tau/\alpha]C) \quad \text{if } \alpha \notin FV(\tau) \\
\mathcal{U}(\{(\tau_1 \to \tau_2, \tau'_1 \to \tau'_2)\} \cup C) &= \mathcal{U}(\{(\tau_1, \tau'_1), (\tau_2, \tau'_2)\} \cup C) \\
\mathcal{U}(\{([\tau], [\tau'])\} \cup C) &= \mathcal{U}(\{(\tau, \tau')\} \cup C) \\
\mathcal{U}(\{((\tau_1, \ldots, \tau_n), (\tau'_1, \ldots, \tau'_n))\} \cup C) &= \mathcal{U}(\{(\tau_1, \tau'_1), \ldots, (\tau_n, \tau'_n)\} \cup C) \\
\mathcal{U}(\{(T\langle\tau_1, \ldots, \tau_n\rangle, T\langle\tau'_1, \ldots, \tau'_n\rangle)\} \cup C) &= \mathcal{U}(\{(\tau_1, \tau'_1), \ldots, (\tau_n, \tau'_n)\} \cup C)
\end{align*}

The occurs check ($\alpha \notin FV(\tau)$) prevents infinite types.

\textbf{Type Inference Algorithm:}

The complete type inference algorithm for expression $e$ in environment $\Gamma$:

\begin{enumerate}
\item Generate constraints: $(\tau, C) = \mathcal{C}(\Gamma, e)$
\item Solve constraints: $S = \mathcal{U}(C)$
\item Apply substitution: $\tau' = S(\tau)$
\item Generalize: $\sigma = \text{gen}(S(\Gamma), \tau')$
\end{enumerate}

The result is the principal type scheme $\sigma$.

\textbf{Soundness and Completeness:}

The type inference algorithm is sound (if inference succeeds, the program is well-typed) and complete (if a typing exists, inference finds the principal type). This is guaranteed by the properties of Algorithm W for Hindley-Milner type systems.

\subsection{Dynamic Semantics}

\subsubsection{Notation}

We employ the following notation for dynamic semantics:

\textbf{Syntactic Categories:}
\begin{itemize}
\item $e$ ranges over expressions
\item $v$ ranges over values
\item $p$ ranges over patterns
\item $x$ ranges over variables
\item $n$ ranges over integer literals
\item $b$ ranges over boolean literals (\texttt{true}, \texttt{false})
\item $C$ ranges over constructors
\end{itemize}

\textbf{Values:}
Values are the results of evaluation and include:
\begin{itemize}
\item Integer values: $n$
\item Boolean values: $b$
\item Unit value: $()$
\item String values: $s$
\item List values: $[]$ (empty list), $v_1 :: v_2$ (cons)
\item Tuple values: $(v_1, v_2, \ldots, v_n)$
\item Closure values: $\langle \texttt{fn} \; p \; \texttt{->} \; e, \rho \rangle$ representing a function with parameter pattern $p$, body $e$, and captured environment $\rho$
\item Constructor values: $C(v)$ representing algebraic data type constructors applied to values
\end{itemize}

\textbf{Environments:}
$\rho$ denotes value environments, which are finite maps from variables to values, written as $\{x_1 \mapsto v_1, \ldots, x_n \mapsto v_n\}$. We write:
\begin{itemize}
\item $\rho(x)$ for environment lookup, returning the value bound to $x$
\item $\rho[x \mapsto v]$ for environment extension, binding $x$ to $v$
\item $\emptyset$ for the empty environment
\item $\rho_1 + \rho_2$ for environment union (right-biased: $\rho_2$ shadows $\rho_1$)
\end{itemize}

\textbf{Evaluation Judgment:}
The primary judgment form is:
$$\langle e, \rho \rangle \Downarrow v$$
read as ``expression $e$ evaluates to value $v$ in environment $\rho$.''

\textbf{Pattern Matching:}
Pattern matching produces bindings from patterns and values. We write:
$$\texttt{match}(p, v) = \rho$$
to indicate that pattern $p$ successfully matches value $v$, producing environment $\rho$ containing the bindings. If matching fails, we write $\texttt{match}(p, v) = \bot$ (failure).

\textbf{Auxiliary Notation:}
\begin{itemize}
\item $\{e_i\}_{i=1}^{n}$ denotes a sequence of expressions $e_1, \ldots, e_n$
\item $\{v_i\}_{i=1}^{n}$ denotes a sequence of values $v_1, \ldots, v_n$
\item Inference rules are written with premises above the line and conclusion below
\item Side conditions are written to the right of rules when necessary
\end{itemize}

\subsubsection{Evaluation Rules}

We now present the complete evaluation rules for LambdaScript expressions.

\textbf{Literals:}

$$\frac{}{\langle n, \rho \rangle \Downarrow n}
\quad
\frac{}{\langle b, \rho \rangle \Downarrow b}
\quad
\frac{}{\langle s, \rho \rangle \Downarrow s}
\quad
\frac{}{\langle (), \rho \rangle \Downarrow ()}$$

\textbf{Variables:}

$$\frac{x \mapsto v \in \rho}{\langle x, \rho \rangle \Downarrow v}$$

\textbf{Functions (Closures):}

$$\frac{}{\langle \texttt{fn} \; p \; \texttt{->} \; e, \rho \rangle \Downarrow \langle \texttt{fn} \; p \; \texttt{->} \; e, \rho \rangle}$$

A function expression evaluates to a closure capturing the current environment.

\textbf{Application:}

$$\frac{\langle e_1, \rho \rangle \Downarrow \langle \texttt{fn} \; p \; \texttt{->} \; e, \rho' \rangle \quad \langle e_2, \rho \rangle \Downarrow v_2 \quad \texttt{match}(p, v_2) = \rho'' \quad \langle e, \rho' + \rho'' \rangle \Downarrow v}{\langle e_1 \; e_2, \rho \rangle \Downarrow v}$$

Application evaluates the function to a closure, evaluates the argument, matches the argument against the parameter pattern, and evaluates the body in the extended environment.

\textbf{Let Binding:}

$$\frac{\langle e_1, \rho \rangle \Downarrow v_1 \quad \texttt{match}(p, v_1) = \rho' \quad \langle e_2, \rho + \rho' \rangle \Downarrow v_2}{\langle \texttt{let} \; p = e_1 \; \texttt{in} \; e_2, \rho \rangle \Downarrow v_2}$$

\textbf{Recursive Let Binding:}

$$\frac{\langle e_1, \rho[x \mapsto \langle \texttt{fn} \; p \; \texttt{->} \; e_1, \rho[x \mapsto \cdots] \rangle] \rangle \Downarrow v_1 \quad \langle e_2, \rho[x \mapsto v_1] \rangle \Downarrow v_2}{\langle \texttt{let rec} \; x \; p = e_1 \; \texttt{in} \; e_2, \rho \rangle \Downarrow v_2}$$

The recursive binding creates a cyclic environment where $x$ is bound to a closure that can refer to itself.

\textbf{Conditional:}

$$\frac{\langle e_1, \rho \rangle \Downarrow \texttt{true} \quad \langle e_2, \rho \rangle \Downarrow v}{\langle \texttt{if} \; e_1 \; \texttt{then} \; e_2 \; \texttt{else} \; e_3, \rho \rangle \Downarrow v}$$

$$\frac{\langle e_1, \rho \rangle \Downarrow \texttt{false} \quad \langle e_3, \rho \rangle \Downarrow v}{\langle \texttt{if} \; e_1 \; \texttt{then} \; e_2 \; \texttt{else} \; e_3, \rho \rangle \Downarrow v}$$

\textbf{Pattern Matching:}

$$\frac{\langle e, \rho \rangle \Downarrow v \quad \texttt{match}(p_i, v) = \rho' \quad \langle e_i, \rho + \rho' \rangle \Downarrow v'}{\langle \texttt{case} \; e \; \texttt{do} \; \{p_j \rightarrow e_j\}_{j=1}^{n}, \rho \rangle \Downarrow v'}$$

where $i$ is the first index such that $\texttt{match}(p_i, v) \neq \bot$.

\textbf{Lists:}

$$\frac{}{\langle [], \rho \rangle \Downarrow []}
\quad
\frac{\langle e_1, \rho \rangle \Downarrow v_1 \quad \langle e_2, \rho \rangle \Downarrow v_2}{\langle e_1 :: e_2, \rho \rangle \Downarrow v_1 :: v_2}$$

\textbf{Tuples:}

$$\frac{\langle e_1, \rho \rangle \Downarrow v_1 \quad \cdots \quad \langle e_n, \rho \rangle \Downarrow v_n}{\langle (e_1, \ldots, e_n), \rho \rangle \Downarrow (v_1, \ldots, v_n)}$$

\textbf{Constructors:}

$$\frac{}{\langle C, \rho \rangle \Downarrow C}
\quad
\frac{\langle e, \rho \rangle \Downarrow v}{\langle C \; e, \rho \rangle \Downarrow C(v)}$$

\textbf{Binary Operators:}

$$\frac{\langle e_1, \rho \rangle \Downarrow n_1 \quad \langle e_2, \rho \rangle \Downarrow n_2 \quad n_3 = n_1 \oplus n_2}{\langle e_1 \; \texttt{op} \; e_2, \rho \rangle \Downarrow n_3}$$

where $\oplus$ denotes the semantic interpretation of the operator.

\subsubsection{Pattern Matching Rules}

The auxiliary function $\texttt{match}(p, v)$ attempts to match pattern $p$ against value $v$, returning an environment of bindings or failure ($\bot$).

\textbf{Variable Pattern:}
$$\texttt{match}(x, v) = \{x \mapsto v\}$$

\textbf{Wildcard Pattern:}
$$\texttt{match}(\_, v) = \emptyset$$

\textbf{Literal Patterns:}
$$\texttt{match}(n, n) = \emptyset
\quad
\texttt{match}(b, b) = \emptyset
\quad
\texttt{match}((), ()) = \emptyset$$

If the literal values don't match: $\texttt{match}(n, n') = \bot$ when $n \neq n'$.

\textbf{List Patterns:}
$$\texttt{match}([], []) = \emptyset$$

$$\texttt{match}(p_1 :: p_2, v_1 :: v_2) = \texttt{match}(p_1, v_1) + \texttt{match}(p_2, v_2)$$

if both sub-matches succeed; otherwise $\bot$.

\textbf{Tuple Patterns:}
$$\texttt{match}((p_1, \ldots, p_n), (v_1, \ldots, v_n)) = \texttt{match}(p_1, v_1) + \cdots + \texttt{match}(p_n, v_n)$$

if all sub-matches succeed; otherwise $\bot$.

\textbf{Constructor Patterns:}
$$\texttt{match}(C, C) = \emptyset$$

$$\texttt{match}(C \; p, C(v)) = \texttt{match}(p, v)$$

If constructors don't match: $\texttt{match}(C, C') = \bot$ when $C \neq C'$.

\subsubsection{Evaluation Examples}

\textbf{Example 1: Function Application}

Consider evaluating \texttt{(fn x -> x + 1) 5} in empty environment $\emptyset$:

\begin{enumerate}
\item $\langle \texttt{fn} \; x \; \texttt{->} \; x + 1, \emptyset \rangle \Downarrow \langle \texttt{fn} \; x \; \texttt{->} \; x + 1, \emptyset \rangle$
\item $\langle 5, \emptyset \rangle \Downarrow 5$
\item $\texttt{match}(x, 5) = \{x \mapsto 5\}$
\item $\langle x + 1, \{x \mapsto 5\} \rangle \Downarrow 6$
\item Therefore: $\langle \texttt{(fn} \; x \; \texttt{->} \; x + 1) \; 5, \emptyset \rangle \Downarrow 6$
\end{enumerate}

\textbf{Example 2: Pattern Matching on Lists}

Evaluating \texttt{case [1, 2] do | [] -> 0 | h :: t -> h} in $\emptyset$:

\begin{enumerate}
\item $\langle [1, 2], \emptyset \rangle \Downarrow 1 :: (2 :: [])$
\item First pattern $[]$ fails: $\texttt{match}([], 1 :: (2 :: [])) = \bot$
\item Second pattern $h :: t$ succeeds: $\texttt{match}(h :: t, 1 :: (2 :: [])) = \{h \mapsto 1, t \mapsto 2 :: []\}$
\item $\langle h, \{h \mapsto 1, t \mapsto 2 :: []\} \rangle \Downarrow 1$
\item Result: $1$
\end{enumerate}

These operational semantics define the complete runtime behavior of LambdaScript and provide a formal foundation for reasoning about program correctness.

\section{Implementation}

The LambdaScript interpreter is implemented in OCaml and consists of a multi-pass pipeline that transforms source code into typed, evaluated results. This section describes the architecture and implementation details of each component.

\subsection{Architecture Overview}

The interpreter follows a traditional compiler pipeline architecture with the following phases:

\begin{enumerate}
\item \textbf{Lexical Analysis (Lexer)}: Tokenizes source code into a stream of tokens
\item \textbf{Syntactic Analysis (Parser)}: Constructs an abstract syntax tree (AST) from tokens using parser combinators
\item \textbf{AST Simplification}: Transforms the parser AST into a condensed representation suitable for type checking
\item \textbf{Type Inference}: Performs constraint-based type inference using Algorithm W
\item \textbf{Type Fixing}: Resolves recursive types and applies type substitutions throughout the AST
\item \textbf{Evaluation}: Interprets the typed AST using environment-based semantics
\end{enumerate}

The implementation uses two distinct AST representations:

\begin{itemize}
\item \textbf{Parser AST} (\texttt{Expr.expr}): A surface-level representation that closely mirrors the concrete syntax, preserving operator precedence information and syntactic structure
\item \textbf{Core AST} (\texttt{Cexpr.c\_expr}): A simplified representation optimized for type checking and evaluation, with explicit operator applications and normalized structure
\end{itemize}

This two-stage approach separates parsing concerns from semantic analysis, allowing the parser to focus on syntactic correctness while the core representation facilitates type inference and evaluation.

\subsection{Lexer and Parser}

\subsubsection{Lexical Analysis}

The lexer (\texttt{lex.ml}) implements a token-based scanner that transforms source code into a sequence of tokens. Tokens represent atomic lexical units such as keywords, identifiers, literals, and operators.

\textit{Token types include:}
\begin{itemize}
\item \textbf{Literals}: \texttt{Integer}, \texttt{FloatToken}, \texttt{Boolean}, \texttt{CharToken}, \texttt{StringToken}
\item \textbf{Keywords}: \texttt{Let}, \texttt{Rec}, \texttt{And}, \texttt{In}, \texttt{If}, \texttt{Then}, \texttt{Else}, \texttt{Case}, \texttt{Do}, \texttt{Fn}, \texttt{Type}
\item \textbf{Identifiers}: \texttt{Id} (lowercase), \texttt{TypeVar} (starts with \texttt{'}), type constructors
\item \textbf{Operators}: \texttt{Plus}, \texttt{Minus}, \texttt{Times}, \texttt{Divide}, \texttt{Mod}, \texttt{AND}, \texttt{OR}, \texttt{ConsToken} (\texttt{::})
\item \textbf{Comparison}: \texttt{EQ}, \texttt{NE}, \texttt{LT}, \texttt{GT}, \texttt{LE}, \texttt{GE}
\item \textbf{Delimiters}: \texttt{LParen}, \texttt{RParen}, \texttt{LBracket}, \texttt{RBracket}, \texttt{LBrace}, \texttt{RBrace}
\item \textbf{Custom operators}: \texttt{Relop}, \texttt{Addop}, \texttt{Mulop}, \texttt{Logop} for user-defined operators
\end{itemize}

The lexer maintains line number information for each token, enabling precise error reporting. String and character literals support escape sequences (\texttt{\textbackslash n}, \texttt{\textbackslash t}, \texttt{\textbackslash"}, etc.). Comments are handled using OCaml-style syntax: \texttt{(* ... *)}.

\subsubsection{Parser Combinators}

The parser (\texttt{parser.ml}) uses a combinator-based approach, defining a parser as a function from token streams to optional parse results:

\begin{quote}
\small
\begin{verbatim}
type 'a parser = 
  token_type list -> ('a * token_type list) option
\end{verbatim}
\end{quote}

Parser combinators provide compositional building blocks:

\begin{itemize}
\item \texttt{<|>} (choice): Tries first parser; if it fails, tries second parser
\item \texttt{>>} (sequence): Chains parsers, passing results forward
\item \texttt{*>} (right): Sequences two parsers, keeping right result
\item \texttt{<*} (left): Sequences two parsers, keeping left result
\item \texttt{>>=} (bind): Monadic bind for dependent parsing
\end{itemize}

\textit{Example combinator usage:}

\begin{quote}
\small
\begin{verbatim}
(* Parse "if e1 then e2 else e3" *)
let if_parser = 
  keyword If *> 
  expr_parser >>= fun e1 ->
  keyword Then *>
  expr_parser >>= fun e2 ->
  keyword Else *>
  expr_parser >>= fun e3 ->
  return (Ternary (e1, e2, e3))
\end{verbatim}
\end{quote}

The parser handles operator precedence through a stratified grammar with separate parsing levels for disjunction (\texttt{||}), conjunction (\texttt{\&\&}), comparison, cons (\texttt{::}), addition, multiplication, and atomic expressions. This ensures correct precedence without explicit precedence tables.

Pattern parsing supports all pattern forms including literals, variables, wildcards, cons patterns, tuples, and constructor applications. Type annotations are parsed alongside expressions and patterns, allowing optional type information at function parameters and let bindings.

\subsection{Type Inference Engine}

The type inference engine (\texttt{typecheck.ml}) implements a constraint-based variant of Algorithm W, the classical Hindley-Milner type inference algorithm. Type inference proceeds in three phases: constraint generation, unification, and generalization.

\subsubsection{Constraint Generation}

Given an expression and a typing environment, constraint generation produces a type (possibly containing fresh type variables) and a set of type equations that must be satisfied for the expression to be well-typed.

The constraint generation function has type:
\begin{quote}
\small
\begin{verbatim}
generate : type_env -> c_expr -> 
  (mono_type * type_equations)
\end{verbatim}
\end{quote}

Fresh type variables are generated using a counter-based approach, ensuring unique identifiers for each unknown type. Constraints are accumulated as the expression tree is traversed.

\textit{Example constraint generation:}

For function application \texttt{e1 e2}:
\begin{enumerate}
\item Generate constraints for \texttt{e1}, obtaining type $\tau_1$ and constraints $C_1$
\item Generate constraints for \texttt{e2}, obtaining type $\tau_2$ and constraints $C_2$
\item Create fresh type variable $\alpha$ for the result
\item Add constraint $\tau_1 = \tau_2 \to \alpha$
\item Return type $\alpha$ with constraints $C_1 \cup C_2 \cup \{(\tau_1, \tau_2 \to \alpha)\}$
\end{enumerate}

Let-bound variables require special handling to support polymorphism. After inferring the type of the bound expression, we solve its constraints, then generalize the resulting type before adding it to the environment for the body. This implements let-polymorphism, allowing expressions like:

\begin{quote}
\small
\begin{verbatim}
let id = fn x -> x in
(id 5, id "hello")
\end{verbatim}
\end{quote}

where \texttt{id} is used at both \texttt{int -> int} and \texttt{string -> string}.

\subsubsection{Unification}

The unification algorithm solves a set of type equations by computing a most general unifier (MGU)—a substitution that, when applied to both sides of each equation, makes them equal.

\textit{Unification rules:}

\begin{itemize}
\item $\mathcal{U}(\alpha, \tau)$: If $\alpha$ does not occur in $\tau$, return $[\tau/\alpha]$; otherwise fail (occurs check)
\item $\mathcal{U}(\tau, \alpha)$: Symmetric to above
\item $\mathcal{U}(\tau_1 \to \tau_2, \tau'_1 \to \tau'_2)$: Recursively unify $\tau_1$ with $\tau'_1$ and $\tau_2$ with $\tau'_2$
\item $\mathcal{U}([\tau], [\tau'])$: Recursively unify $\tau$ with $\tau'$
\item $\mathcal{U}((\tau_1, \ldots, \tau_n), (\tau'_1, \ldots, \tau'_n))$: Recursively unify each pair
\item $\mathcal{U}(T\langle\tau_1, \ldots, \tau_n\rangle, T\langle\tau'_1, \ldots, \tau'_n\rangle)$: Unify type applications
\end{itemize}

The occurs check prevents infinite types by ensuring a type variable does not appear in its own definition. For recursive types, we use explicit fixed-point type constructors (\texttt{FixedPoint}) rather than allowing infinite unfolding.

Type errors are reported when:
\begin{itemize}
\item A type variable occurs in its substituted type (occurs check failure)
\item Two primitive types are equated (e.g., \texttt{int = bool})
\item Type constructors have different arities or names
\item Patterns and scrutinees have incompatible types
\end{itemize}

\subsubsection{Generalization and Instantiation}

After constraint solving, types are generalized by introducing universal quantifiers for free type variables. The generalization function:

$$\text{gen}(\Gamma, \tau) = \forall \{\alpha_1, \ldots, \alpha_n\}.\tau$$

where $\{\alpha_1, \ldots, \alpha_n\} = FV(\tau) \setminus FV(\Gamma)$.

Type schemes are instantiated by replacing quantified variables with fresh type variables:

$$\text{inst}(\forall \alpha.\sigma) = \sigma[\beta/\alpha]$$

This allows polymorphic functions to be used at multiple types while maintaining type safety.

\subsubsection{Type Fixing}

After type inference, the type fixer (\texttt{typefixer.ml}) applies the computed substitution throughout the entire AST, replacing type variables with their inferred types. This phase also:

\begin{itemize}
\item Resolves recursive type references using fixed-point constructors
\item Validates that all type variables have been instantiated
\item Ensures mutually recursive types reference each other correctly
\item Annotates the AST with complete type information for evaluation
\end{itemize}

\subsection{Pattern Matching}

Pattern matching in LambdaScript supports comprehensive destructuring with exhaustiveness checking and redundancy detection.

\subsubsection{Pattern Compilation}

Patterns are compiled into decision trees that efficiently test values against pattern structure. The compilation process:

\begin{enumerate}
\item \textbf{Flattening}: Nested patterns are flattened into sequences of simple tests
\item \textbf{Grouping}: Patterns with the same constructor are grouped together
\item \textbf{Optimization}: Redundant tests are eliminated
\end{enumerate}

Pattern matching executes by traversing the decision tree, testing each pattern in order until a match is found. Variable bindings are collected during matching and added to the evaluation environment.

\subsubsection{Exhaustiveness Checking}

The exhaustiveness checker (\texttt{exhaustiveness.ml}) ensures that pattern matches cover all possible values. This analysis prevents runtime match failures by detecting missing cases at compile time.

The algorithm constructs a symbolic representation of the input space and removes the portion covered by each pattern. If any portion remains uncovered, the match is non-exhaustive and an error is reported.

\textit{Example exhaustiveness violations:}

\begin{quote}
\small
\begin{verbatim}
(* Non-exhaustive: missing Nil case *)
case lst do
| h :: t -> h

(* Exhaustive: all cases covered *)
case lst do
| [] -> 0
| h :: t -> h
\end{verbatim}
\end{quote}

For user-defined algebraic data types, exhaustiveness checking verifies that all constructors are matched. Wildcard patterns and variable patterns match any value, making the entire match exhaustive if they appear as the final case.

\subsection{Evaluator}

The evaluator (\texttt{ceval.ml}) implements the operational semantics using environment-based interpretation with closures.

\subsubsection{Value Representation}

Values are the results of evaluation:

\begin{quote}
\small
\begin{verbatim}
type value =
  | IntVal of int
  | BoolVal of bool
  | StringVal of string
  | CharVal of char
  | UnitVal
  | ListVal of value list
  | TupleVal of value list
  | ClosureVal of c_pat * c_expr * env
  | ConstructorVal of string * value option
\end{verbatim}
\end{quote}

Closures capture their defining environment, enabling proper handling of free variables and supporting higher-order functions with lexical scoping.

\subsubsection{Environment-Based Evaluation}

Environments map variable names to values. Evaluation judgments have the form:

$$\langle e, \rho \rangle \Downarrow v$$

The evaluator recursively descends the expression tree, accumulating bindings in the environment and producing values.

\textit{Key evaluation rules:}

\begin{itemize}
\item \textbf{Variables}: Look up in environment, fail if unbound
\item \textbf{Functions}: Create closure capturing current environment
\item \textbf{Application}: Evaluate function to closure, evaluate argument, match pattern against argument value, evaluate body in extended environment
\item \textbf{Let bindings}: Evaluate bound expression, match pattern, extend environment for body
\item \textbf{Recursive let}: Create cyclic environment where bound variable refers to itself
\item \textbf{Pattern matching}: Evaluate scrutinee, try each branch in order until pattern matches
\end{itemize}

\subsubsection{Built-in Functions}

Built-in functions are implemented as primitive operations in the evaluator:

\begin{itemize}
\item \textbf{I/O}: \texttt{print}, \texttt{println}
\item \textbf{Conversions}: \texttt{int\_to\_str}, \texttt{int\_to\_float}, \texttt{float\_to\_int}, \texttt{string\_to\_list}
\item \textbf{Higher-order}: \texttt{map}, \texttt{filter}, \texttt{reduce\_left}, \texttt{reduce\_right}
\end{itemize}

These functions are pre-populated in the initial environment with appropriate types and implementations.

\subsection{Advanced Features}

\subsubsection{Mutually Recursive Types}

Mutually recursive type definitions are handled by:
\begin{enumerate}
\item Adding all type names to the environment simultaneously
\item Type-checking constructor payloads with all names in scope
\item Using fixed-point type constructors to represent cycles
\item Verifying that cycles are guarded by constructors (preventing infinite types)
\end{enumerate}

\subsubsection{List Comprehensions}

List comprehensions desugar into nested \texttt{map} and \texttt{filter} operations:

\begin{quote}
\small
\begin{verbatim}
[x * 2 | x => lst, x > 5]
\end{verbatim}
\end{quote}

desugars to:

\begin{quote}
\small
\begin{verbatim}
map (fn x -> x * 2) 
    (filter (fn x -> x > 5) lst)
\end{verbatim}
\end{quote}

\subsubsection{Custom Operators}

User-defined operators are supported through operator definitions. Operators are first-class values when wrapped in parentheses:

\begin{quote}
\small
\begin{verbatim}
let (++) = fn a -> fn b -> a + b in
(++) 3 4  (* Returns 7 *)
\end{verbatim}
\end{quote}

Custom operators follow the precedence of their first character (\texttt{+}, \texttt{-}, \texttt{*}, \texttt{/}, etc.).

\subsubsection{Code Blocks}

Code blocks provide sequential execution with local definitions:

\begin{quote}
\small
\begin{verbatim}
{
  let x = 5;
  let y = 10;
  x + y
}
\end{verbatim}
\end{quote}

Blocks desugar into nested let expressions, maintaining proper scoping of local bindings.
